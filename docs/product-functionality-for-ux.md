# GPS App 功能清单（面向交互设计）

> 用途：把当前应用的能力从实现细节里剥出来，便于带去设计工具重新规划交互。
> 生成时间：2026-04-25。来源：`docs/backlog.md` + `docs/roadmap/` + 代码现状梳理。
> 注意：本文件只描述"用户视角的功能"和"对交互设计的约束"，不描述实现方案。
> 若与 `docs/backlog.md` 冲突，以 backlog 为准。

## 一、一句话定位

一个配合外接 BLE GPS 接收器（RaceChrono 协议，25Hz）的**车辆性能测试**工具。
核心产出是**加速/刹车成绩**和**赛道圈速**。外设 + 实时数据 + 结果回看是三大支柱。

## 二、核心功能（已实现，需要好交互）

### 1. 加速测试（0–100 km/h）
- 静止起步 → 自动识别加速起点 → 达 100 km/h 完成
- 产出：总耗时、平均/最大加速度、每 10 km/h 分段、速度曲线
- 自动保存，可回看，可语音播报

### 2. 刹车测试（100–0 km/h）
- 巡航 95–105 km/h → 踩刹车触发 → 速度 ≤ 1 km/h 完成
- 产出：制动距离、制动耗时、最大减速度

### 3. 圈速记录（数据已就位，UI 基本空白）
- 基于**预置赛道**（含起终点线与分段线，TimingGate 几何判定）
- 自动识别每圈起止，给出单圈时间、分段时间、多圈列表
- 轨迹采样在跑，但"地图 + 圈次视图 + 最佳圈高亮"基本没做
- GPX/KML 导出规划中，尚无入口

### 4. 历史记录与结果详情
- 列表按时间倒序，长按删除，统计"最佳加速/最佳刹车"
- 详情页有成绩卡 + 速度/G 值曲线；"分段数据"还是从原始点现算，非正式视图

### 5. 智能启动准备
- 测试前做"就绪检查"：BLE 连接、卫星数 ≥6、HDOP<2、数据新鲜度、起点速度范围
- 条件齐 → 5 秒倒计时 → 自动进入记录
- 这套机制本身是好的，UX 上值得保留但需要重新包装

### 6. 语音播报
- 能播"零百 X.X 秒"、"百零 X.X 秒"、"第 N 圈 X 分 X 秒"
- 开关已有；"测试开始 / 结束"触发点待补（P1）

## 三、支撑功能（决定交互是否成立）

### 7. BLE GPS 设备
- 扫描 → 选择 → 连接（RaceChrono 协议，固定 UUID）
- 四态：未连接 / 连接中 / 已连接 / 断开中
- 有 RSSI、卫星数、HDOP、数据频率、质量评级（差/中/良/优）
- "上次设备记忆 + 自动重连"框架在，落地不完整
- **所有测试功能强依赖连接在线 + GPS 锁定**

### 8. 权限引导
- Android 12+ 需要 BLE_SCAN / BLE_CONNECT / FINE_LOCATION
- 目前靠系统默认弹窗，无首启引导页

### 9. 设置
- 已有：语音开关、模拟模式切换（开发用）
- 待做 P0：**加速度模式选择**（标准 / 高性能两档，对应不同过滤阈值），目前无 UI，用户无法改

### 10. 模拟器（simulator）
- 独立 App，不给终端用户。用于开发时 BLE 广播假数据和回放真实数据。
- 交互设计**不用管**。

## 四、规划中（P2/P3，先预留位置，不必现在设计细节）

- **视频录制 + HUD 叠加 + 视频管理**（P2，无代码）：测试中同步录视频，画面上叠速度/G/计时，事后查看分享
- **圈速 UI 与轨迹可视化**（P3）：2D 赛道图 + 当前圈/最佳圈/历史圈对比
- **GPX / KML 导出**（P3）

## 五、当前屏幕现状（哪些是"真 UX"，哪些是"临时堆数据"）

| 屏 | 功能 | 状态 |
|---|---|---|
| 权限请求 | 系统弹窗兜底 | 临时，无自定义引导 |
| 设备连接 | 扫描/连接/信号状态 | 基本成型，UI 朴素 |
| 测试类型选择 | 选加速/刹车/圈速调试 + 填车型 | 功能在，视觉是原型 |
| 智能启动准备 | 5 秒倒计时 + 就绪清单 | 逻辑好，视觉待加工 |
| 测试执行（加速/刹车） | 大字速度 + 进度 + 信号卡 | 基本成型 |
| 测试执行（圈速调试） | Track 占位图 + 传感器卡 | **明显临时**，堆数据 |
| 结果详情 | 成绩 + 曲线图 | 部分成型，分段数据是 TODO |
| 圈速调试结果 | 圈列表 + Crossing 事件 | **纯调试视图**，要重设计 |
| 历史记录 | 列表 + 统计 + 删除 | 基本成型 |
| 设置页 | — | **实质缺失**（加速度模式、单位、重连策略都没有入口）|

## 六、对交互设计的关键约束

1. **全局状态条要常驻**：设备连接态 + GPS 锁定 + 数据质量三要素必须随时可见，它们是测试能否进行的前置闸门
2. **测试前置条件有门槛**：不满足就绪条件不能开测，设计需要把"为什么现在还不能测"讲清楚
3. **测试中断可能来自外部**（BLE 掉线、GPS 失联），需要明确的中断反馈与恢复路径
4. **单位与阈值属于专业设置**：用户可能是普通车主也可能是赛车玩家，设置页需要分级（常用 / 专业）
5. **结果是一等公民**：测试是一次性的，结果才是反复看的，详情页 + 历史对比的分量应该更重
6. **语音是辅助通道**：画面被遮挡/视线在路上时是主要反馈，开关要醒目
7. **未来要给视频留位置**：测试执行页、结果详情页、主导航都要提前预留"视频"容器，避免后续硬塞

## 七、最大的设计缺口（建议优先发力）

1. **首页 / 主导航骨架**：现在是线性堆栈，没有"主页"的概念，所有入口并列挤在"测试类型选择"里。需要决定是底 tab、卡片主页还是单流程
2. **设备连接与状态的常驻表达**：目前只在连接屏可见，测试屏只能看到卡片局部信息
3. **圈速模块的完整 UX**：从选赛道 → 跑圈 → 看单圈/最佳圈/轨迹 → 导出，这条线基本要从 0 设计
4. **结果详情的信息架构**：曲线、分段、地图、对比（和自己历史、和他人）——哪些必现、哪些折叠
5. **设置页的信息架构**：常用（语音、单位、加速度模式）/ 设备（重连策略、协议模式）/ 高级（日志、诊断）
6. **首启引导**：权限、设备配对、单位选择，需要一个正式的 onboarding
