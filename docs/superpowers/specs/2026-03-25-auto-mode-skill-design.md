# Auto Mode Skill 设计规范

> 日期：2026-03-25
> 目标：提供一个手动触发、可切换的 personal skill，使当前 session 在明确执行链路下进入“连续执行、少确认”的协作模式，同时保留对高风险动作的确认边界。

## 1. 设计目标

本设计解决的问题不是权限系统本身，而是协作节奏：

- 用户已经给出明确、确定性的执行链路后，Agent 仍反复询问“是否继续”
- 用户希望通过一个可控、可显式开关的 skill，减少重复确认
- 用户不希望直接把这种偏好写死进项目 `CLAUDE.md`，以避免对所有任务产生副作用

因此该 skill 的目标是：

1. 通过单一命令 `/auto-mode` 进入或退出自动连续执行模式
2. 仅影响当前 session，不污染项目规则
3. 对低风险、本地、可逆动作默认连续推进
4. 对高风险、不可逆、远端或共享状态变更保留单独确认

## 2. 范围与非目标

### 2.1 范围

本 skill 只处理 **协作协议**，不处理以下内容：

- Claude Code 的权限弹窗机制
- 系统级 approval / permission mode 的绕过
- 跨 session 自动同步
- 对旧 session 的远程热更新

### 2.2 非目标

本 skill 不追求：

- 自动替用户点击同意
- 在所有项目、所有 session 中默认开启
- 替代高风险动作前的人类确认

## 3. 触发方式与生命周期

### 3.1 触发方式

用户通过 `/auto-mode` 手动触发。

### 3.2 生命周期

- 第一次调用 `/auto-mode`：开启 auto mode
- 再次调用 `/auto-mode`：关闭 auto mode
- 作用范围：**当前 session**
- 持续时间：直到用户再次调用 `/auto-mode` 关闭

### 3.3 状态管理

skill 需要维护一个**仅当前 session 可见**的状态标记，用于判断当前是开启还是关闭状态。

状态设计要求：

- 不写入项目源码目录
- 不污染业务代码仓库
- 必须按 session 隔离，不能让并行 session 互相污染
- 仅作为 skill 行为切换依据
- 关闭时应移除或清空状态

推荐约束：

- 优先使用 session 内上下文态；如果平台能力不足，再退化为带 session 标识的本地状态文件
- 只有在运行环境能提供可靠且稳定的 session 唯一标识时，才允许使用本地状态文件方案
- 若拿不到可靠 session 标识，则不得使用共享文件式状态持久化，应退回纯 session 内态
- 若使用本地状态文件，文件名必须包含 session 级唯一标识，避免多个 session 共用同一个开关状态
- 该设计不要求跨重启恢复状态；session 结束后状态自然失效
- 设计中必须承认：该状态只对调用过 `/auto-mode` 的当前 session 生效，不自动扩散到其他已运行 session

## 4. 行为规则

### 4.1 开启后的默认行为

当 auto mode 开启后，Agent 应遵循以下执行规则：

- 对已经明确的执行链路，默认连续向下执行
- 对本地、可逆、低风险动作，不逐步重复征求同意
- 避免重复询问以下类型的问题：
  - “要不要继续？”
  - “是否执行下一步？”
  - “要不要我现在做？”
- 只有在遇到真实 blocker、需求不明确、实现分叉明显，或高风险动作时才停下

“明确执行链路”的最小判定标准建议为：

- 用户已明确目标、范围、约束，且当前步骤不存在关键方案分叉
- 下一步动作属于当前任务的显然延续，不需要额外方案决策
- 即使存在多个可行方案，它们的差异也不足以改变用户价值、风险边界或影响范围
- 一旦执行中出现需要重新选方案、扩大影响面、跨模块/跨环境评估，或改变范围边界，应退出自动推进并确认

为避免行为漂移，建议采用最小判定矩阵：

#### 默认可连续推进
- 本地读取、搜索、分析
- 局部代码修改与新增文件（以当前任务直接所需、影响范围局部、且不引入共享外部副作用为前提）
- 本地运行验证、测试、构建
- 明确链路下的后续低风险编辑与修正

#### 默认停下确认
- 远端写操作或会改变共享状态的远端操作
- 删除文件
- 覆盖、回退、丢弃已有改动
- 修改数据库、外部服务、CI/CD、共享环境
- 其他不可逆或高影响操作

#### 需结合上下文判断
- `git commit`
- 批量改动或大范围替换
- 配置文件、权限声明、发布相关脚本修改
- 可能影响多个模块、环境或既有约定的操作

### 4.2 仍需确认的动作边界

即使 auto mode 开启，以下动作仍必须单独确认：

- `git push` 或其他远端写操作
- 创建、更新、关闭 PR / issue，或其他会改变共享状态的远端操作
- 删除文件
- 覆盖、回退、丢弃已有改动
- 修改数据库、外部服务、CI/CD、共享环境
- 其他不可逆或高影响操作

说明：

- 只读远端查询（如 `git fetch`、查看远端信息）不自动归为高风险
- 若某个远端操作虽然表面是查询，但会触发副作用，也归入高风险边界

### 4.3 关闭后的行为

关闭后，恢复常规协作模式：

- 对关键下一步可适度确认
- 不再假定用户希望连续自动推进

## 5. 用户可见反馈

skill 应保持简洁反馈，避免制造额外噪音。

### 5.1 开启时

建议输出：

`Auto mode 已开启：仅当前 session 生效；明确链路下连续执行，仅在高风险动作前确认。`

### 5.2 关闭时

建议输出：

`Auto mode 已关闭：恢复常规确认模式。`

## 6. 技术设计

## 6.1 目录与文件

建议将其实现为 personal skill，例如：

```text
~/.claude/skills/auto-mode/
  SKILL.md
  auto-mode-state.sh   # 可选，若需要状态辅助脚本
```

### 6.2 实现策略

推荐采用“单 skill + 状态切换”模型：

1. `/auto-mode` 被调用
2. 读取当前 session 的状态标记
3. 若未开启：写入开启状态，并输出开启提示
4. 若已开启：移除状态，并输出关闭提示
5. 后续执行过程中，Agent 按 skill 规则约束自己的确认频率

### 6.3 约束策略

该 skill 的核心不是执行复杂逻辑，而是提供一个明确、稳定、可复用的行为协议。

因此实现上应拆分为两层：

- **协议层**：定义开启后/关闭后应遵循的行为规则、风险边界与反馈文案
- **状态层**：只负责当前 session 下的开关态存取与切换

skill 本身负责触发 toggle，并向后续对话暴露一个明确状态。

此外应明确优先级：

- auto mode 只调整“是否对低风险下一步重复确认”的协作节奏
- 不覆盖系统规则、全局规则、项目规则中的安全边界
- 若规则冲突，以更严格边界优先

## 7. 测试与验证策略

由于这是一个 skill，验证方式应遵循“文档型 TDD”而不是业务代码测试。

### 7.1 RED：基线失败场景

在未配置该 skill 时，构造以下压力场景并记录 Agent 的自然失败模式：

1. 用户已明确给出多步连续链路，Agent 仍逐步确认
2. 用户已说明偏好自驱，Agent 仍在每步前等待许可
3. 低风险本地动作存在明确下一步，Agent 仍停下来征求继续许可

### 7.2 GREEN：skill 生效后的通过标准

启用该 skill 后，应满足：

1. 在明确链路下连续推进
2. 不对低风险本地动作重复确认
3. 在高风险动作前仍停下确认
4. 开启与关闭反馈明确可感知

### 7.3 REFACTOR：补漏洞

若测试中出现新的合理化路径，需在 skill 中补充：

- 典型错误借口
- 红旗清单
- 对“明确链路”“高风险动作”的边界说明

## 8. 风险与限制

### 8.1 已知限制

- 无法绕过 Claude Code 原生权限确认
- 无法自动影响已经启动且未调用该 skill 的其他 session
- 若当前任务本身存在歧义，仍需正常提问澄清
- 需求仍在探索阶段、存在明显方案分叉或影响跨模块/跨环境时，不应依赖 auto mode 直接推进

### 8.2 风险控制

通过显式保留高风险确认边界，避免 auto mode 误扩展到：

- 远端共享状态变更
- 不可逆操作
- 数据或环境破坏性动作
- 批量重命名、大范围替换、发布配置或权限项调整等高影响变更

## 9. 验收标准

满足以下条件即可认为该设计达成目标：

- 存在单一命令 `/auto-mode`
- 同一命令可完成开启/关闭切换
- 作用范围仅限当前 session
- 不改项目 `CLAUDE.md`
- 对低风险本地动作减少重复确认
- 对高风险动作仍强制确认
- 用户可通过简短反馈感知当前状态

## 10. 后续实施建议

实施阶段应先完成两部分：

1. **skill 文档本体**：明确触发条件、开关规则、边界、红旗与常见误区
2. **最小状态机制**：确保 `/auto-mode` 可在当前 session 中完成切换

在此基础上，再做一次压力场景验证，确认它确实减少重复确认，而不是只改变说明文字。
