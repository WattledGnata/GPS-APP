# GPS App 需求清单协作机制设计

> 日期：2026-03-24
> 目标：为 GPS App 建立一份长期维护的共享需求清单，作为后续需求排期、实现顺序、影响评估、验收流转与自驱开发的统一入口。

## 1. 背景

当前项目已经有部分规划与设计文档，但入口分散：

- `docs/roadmap/2026-03-23-future-features-roadmap.md` 记录了部分后续能力和优先级
- `docs/superpowers/specs/*.md` 记录了单个主题的设计文档
- `docs/CHANGELOG.md` 记录了已完成改动

这些文档可以提供历史上下文，但还缺少一份**长期维护、面向执行的共享需求清单**，用于回答以下问题：

1. 当前最该做什么？
2. 哪些需求已经开发完成但还没验收？
3. 哪些需求已经正式验收通过？
4. 一个新需求与历史需求、已有设计之间有什么关联？

因此需要增加一份轻量但稳定的 backlog 文档，让后续协作默认以 backlog 为主入口，设计文档作为重要需求的详细展开。

## 2. 设计目标

这份需求清单需要满足：

- 作为项目需求的**唯一执行入口**
- 支持用户按需调整优先级
- 支持 AI 在开始新需求前先参考历史需求和已有设计
- 区分“开发完成”和“验收通过”两个阶段
- 对重要需求可链接到独立 spec 文档
- 让后续拆解型任务可以沿着 backlog 连续推进，减少反复确认

## 3. 总体方案

采用 **单文件 backlog + 重要需求链接 spec** 的方式。

- 固定入口文件：`docs/backlog.md`
- backlog 中维护所有待办、进行中、待验收、已验收的需求条目
- 重要需求若需要更完整设计，再链接到 `docs/superpowers/specs/YYYY-MM-DD-*.md`

该方案有以下优点：

- 对用户而言最容易直接阅读和手工调整
- 对 Claude 而言有稳定入口，适合按优先级连续执行
- 与项目现有 `roadmap` 和 `specs` 文档兼容，不需要重建流程
- 比 OpenSpec 更轻，适合当前项目节奏

## 4. backlog 文件位置与角色

### 4.1 文件位置

- 主文件：`docs/backlog.md`

### 4.2 角色分工

- `docs/backlog.md`：执行入口、状态源、优先级源
- `docs/superpowers/specs/*.md`：复杂需求的详细设计说明
- `docs/roadmap/*.md`：中长期想法与未来规划，可作为 backlog 的来源之一
- `docs/CHANGELOG.md`：已落地改动的历史记录，可作为 backlog 的验收后补充信息来源

### 4.3 文档关系

推荐关系如下：

```text
roadmap / 用户新想法
        ↓
    backlog 条目
        ↓
复杂需求补 spec
        ↓
实现完成 -> done
        ↓
用户验收 -> accepted
```

## 5. 条目结构

每个 backlog 条目包含以下字段：

- **标题**：需求名称，作为主要识别方式
- **优先级**：`P0 / P1 / P2 / P3`
- **状态**：`todo / doing / done / accepted`
- **影响范围**：预计涉及的模块、目录、功能区域
- **验收标准**：用户可直接判断是否通过的条件
- **关联 spec**：如有复杂设计，对应 spec 路径
- **关联历史**：来源、上下文、历史需求或备注

其中不要求单独维护稳定编号，避免为了编号管理带来额外负担。后续沟通时默认用“标题”来引用需求。

## 6. 优先级规则

采用四级优先级：

- `P0`：立即处理，影响当前关键功能或当前验收
- `P1`：近期处理，明确要做，价值较高
- `P2`：中期处理，暂不阻塞当前版本
- `P3`：长期想法或预研方向

默认执行顺序：

1. 先按优先级排序（P0 → P1 → P2 → P3）
2. 同优先级下优先处理更明确、依赖更少、已有 spec 的需求
3. 用户人工调整优先级时，以用户调整为准

## 7. 状态流转

采用四状态流转：

- `todo`：未开始
- `doing`：实现中
- `done`：代码已完成，等待用户验收
- `accepted`：用户验收通过，正式完成

状态流转约束：

```text
todo -> doing -> done -> accepted
```

补充规则：

- 只有在用户明确验收通过后，才可从 `done` 改为 `accepted`
- `accepted` 条目可使用勾选形式标识为完成
- 若验收未通过，可从 `done` 回退到 `doing`

## 8. 默认协作规则

在该项目中，后续默认按以下方式协作：

1. 开始新需求前，先查看 `docs/backlog.md`
2. 从高优先级条目中选择下一个可执行需求
3. 开始前结合以下信息评估影响：
   - 条目的影响范围
   - 关联 spec
   - 关联历史
   - 已有 roadmap / changelog / 设计文档
4. 实现过程中将需求状态更新为 `doing`
5. 代码完成后更新为 `done`
6. 用户验收通过后更新为 `accepted`

默认情况下，Claude 应尽量沿着 backlog 连续推进，而不是每完成一个独立小点就停下等待新的会话触发。

## 9. backlog 推荐结构

`docs/backlog.md` 推荐分为以下部分：

1. 文档说明
2. 需求协作规则摘要
3. 当前优先级总览
4. `todo` 条目（按 P0-P3 排序）
5. `doing` 条目
6. `done` 条目（待验收）
7. `accepted` 条目（已验收）
8. backlog 维护规则

这样既能看当前排队需求，也能快速区分“开发中 / 待验收 / 已验收”。

## 10. backlog 条目模板

建议条目模板如下：

```md
## 语音播报补全触发点

- 优先级：P1
- 状态：done
- 影响范围：`app`、`feature/test`
- 验收标准：
  - 测试开始时播报“测试开始”
  - 测试结束时播报成绩
  - 关闭语音开关后不再播报
- 关联 spec：`docs/superpowers/specs/2026-03-xx-voice-announcer-design.md`
- 关联历史：
  - 来源：`docs/roadmap/2026-03-23-future-features-roadmap.md`
  - 与测试流程播报能力有关
```

对于已验收条目，可写为：

```md
## 加速度阈值调整

- 优先级：P0
- 状态：accepted
- 验收结果：已通过
- 影响范围：`app`
- 验收标准：
  - 加速度上限调整为 2.5G
  - 刹车上限调整为 3.0G
- 关联历史：
  - 来源：`docs/roadmap/2026-03-23-future-features-roadmap.md`
```

## 11. 与现有文档的衔接

基于当前项目现状，第一版 backlog 可以吸收以下现有信息：

- `docs/roadmap/2026-03-23-future-features-roadmap.md`
  - 可转入 backlog 的条目：
    - 添加设置页面让用户选择模式
    - 在 TestSessionViewModel 中补全语音播报触发点
    - 视频拍摄 + 图层叠加
    - 完整圈速记录功能
- `docs/CHANGELOG.md`
  - 可辅助判断某些需求是否已完成或已被拆分实现
- `docs/superpowers/specs/*.md`
  - 对后续复杂主题继续保留 spec 入口，不与 backlog 冲突

## 12. 后续实施建议

第一步建议执行以下内容：

1. 创建 `docs/backlog.md`
2. 写入文档说明和协作规则
3. 将当前 roadmap 中已经明确的事项整理为初始 backlog 条目
4. 区分：
   - 已经完成并可视为 `accepted` 的条目
   - 尚未完成的 `todo` 条目
   - 已做未验收的 `done` 条目
5. 未来新增需求时，优先补入 backlog，再决定是否需要独立 spec

## 13. 结论

本设计选择 **轻量 backlog 作为执行主入口，spec 作为复杂需求展开文档**。

这样可以在不引入过重流程的前提下，建立一个可长期维护、可持续推进、适合人机协作的需求管理方式，并与当前项目已有文档体系自然衔接。
