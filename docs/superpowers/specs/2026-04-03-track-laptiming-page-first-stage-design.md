# Track/LapTiming 正式页面第一阶段设计

## 背景

当前圈速相关工作已经形成明确分层：

1. `起点 + s1` 已具备较高可信度，可用于确认主链路成立；
2. `s2` 当前更像是资产定义或版本不一致的局部问题，不应继续阻塞整体页面方向；
3. 现有 `lap-debug-mode` 页面与 `TestSessionViewModel` 仍主要围绕 `LapDebugAnalyzer`、参考点命中、候选圈等中间态调试语义构建；
4. 用户已确认下一步选择 **正式替换到 Track/LapTimingEngine 驱动页面**，但第一版只支持 **`起点 + s1`**。

因此，本轮设计目标不是继续扩写验证壳子，而是把当前页面语义正式切换到 Track/LapTimingEngine 主链路，同时明确第一阶段能力边界。

## 目标

将 `lap-debug-mode` 从基于 `LapDebugAnalyzer` 的参考点调试流，重构为基于 `Track + LapTimingEngine` 的正式圈速入口第一阶段页面。

第一阶段只支持：
- `起点`
- `s1`

不承诺：
- `s2`
- 完整三门 split
- 最终完整圈速产品态

## 非目标

本轮不做以下事项：

- 不解决 `s2` 资产真值问题；
- 不把页面做成完整三门圈速产品页；
- 不引入可切换的“调试模式 / 正式模式”双轨语义；
- 不在本轮处理服务端 Track 下发、用户自定义赛道、轨迹自动生成赛道；
- 不继续围绕 `LapDebugAnalyzer` 强化 candidate lap 展示。

## 设计决策

### 决策 1：页面定位

`lap-debug-mode` 在本轮之后不再定义为“验证壳子”，而定义为：

**正式圈速入口的第一阶段实现。**

但第一阶段能力边界明确受限于 `起点 + s1`。页面必须显式表达这是一个“第一阶段正式入口”，而不是完整圈速产品。

### 决策 2：主状态来源

页面主状态不再以 `LapDebugAnalyzer` 的输出为核心，而应以：

- `Track`
- `TimingGate`
- `LapTimingEngine`
- `LapSession` / crossing 结果

作为页面核心语义来源。

`LapDebugAnalyzer` 若暂时保留，只能作为过渡期内部兼容辅助，不得继续决定页面主展示结构。

### 决策 3：能力边界表达

页面需要明确告诉用户：

- 当前版本只验证 `起点 + s1`
- `s2` 暂未纳入第一阶段能力范围
- 当前结果表示“主链路已进入正式圈速入口化”，不表示完整三门已完成

这个边界必须体现在配置页、执行页、结果页文案与数据结构上，而不能只停留在开发者认知里。

## 页面结构设计

### 1. 选择页

保留“正式测试”与“圈速模式”分流，但圈速入口文案应从“圈速调试”逐步收敛成更接近正式能力的表述。

第一阶段建议：
- 保留入口位置不变，避免扩大导航改动；
- 入口语义从“圈速调试”改成“圈速记录（第一阶段）”或等价表达；
- 在副文案中明确：当前支持 `起点 + s1`。

### 2. 配置页

配置页不再以“参考点命中调试配置”为中心，而改为“第一阶段圈速记录配置”。

保留：
- Track/验证方案选择（若本轮只支持单一 Track，可先做静态展示）；
- 当前能力说明：只支持 `起点 + s1`；
- 必要的基础显示选项（如是否显示轨迹）。

移除或弱化：
- 参考点来源切换；
- 手动经纬度输入；
- 以“命中阈值”为核心的调试参数表达。

原因：这些是旧的参考点调试模型语义，不适合作为正式圈速入口的第一屏核心配置。

### 3. 执行页

执行页应成为“圈速状态观测页”，而不是“参考点命中调试页”。

核心展示应包括：
- 当前 session 状态（待开始 / 记录中 / 已完成阶段结果）；
- 当前 Track 名称与阶段说明；
- 当前已确认的 gate 进度：`起点`、`s1`；
- 最近 crossing 事件；
- 基础 GPS/轨迹观测；
- 明确提示 `s2` 暂不在第一阶段范围内。

弱化或移除：
- `candidateLaps` 为核心的状态展示；
- “命中参考点”作为页面主语义；
- 仅服务于 `LapDebugAnalyzer` 的结果提示。

### 4. 结果页

结果页应表达“本次第一阶段圈速链路是否成立”，而不是输出候选圈调试结果。

核心展示：
- crossing 顺序摘要；
- 是否完成 `起点 -> s1 -> 起点` 的阶段链路；
- 第一阶段可用的耗时结果（如果已有稳定定义）；
- 会话配置快照；
- 轨迹与调试说明。

不作为主体展示：
- candidate lap 列表；
- 旧参考点命中统计作为最终结果主体。

## 数据与状态设计

### 页面核心状态

页面应围绕以下正式对象组织：

- `Track`
  - 当前第一阶段采用预置 Track
  - 只暴露 `起点 + s1`
- `LapSession`
  - 表达当前会话状态
- crossing events
  - 表达当前已识别的 gate 经过情况
- 第一阶段结果摘要
  - 表达是否完成受限版链路

### 过渡策略

为了控制改动风险，可以采用以下过渡策略：

1. 保留原导航骨架；
2. 保留页面路由名，避免同时做大量导航改名；
3. 优先替换页面内部语义和 ViewModel 状态来源；
4. 若必须保留旧字段，需把它们降级为兼容层，而非页面主字段。

## 错误处理与边界

### 明确边界

页面必须显式处理以下情形：

- Track 尚未准备好；
- 当前会话尚未识别到 `起点` crossing；
- 已识别 `起点`，但未识别 `s1`；
- 第一阶段链路未闭合；
- `s2` 当前不参与结果判断。

### 不允许的错误策略

- 不允许为了让页面“看起来完整”而继续展示旧 `candidate lap` 作为主结果；
- 不允许把 `s2` 缺失伪装成“完整能力已具备”；
- 不允许在页面层面放大全局容差或绕过主引擎语义。

## 测试策略

第一阶段页面替换后，测试应重点覆盖：

1. ViewModel 状态是否已从 `LapDebugAnalyzer` 主导切换到 `Track/LapTimingEngine` 主导；
2. 配置页是否清楚表达第一阶段只支持 `起点 + s1`；
3. 执行页是否正确显示 crossing 进度与当前阶段；
4. 结果页是否围绕第一阶段链路结果，而非 candidate lap；
5. 页面是否没有继续把 `s2` 当作前置成功条件。

## 成功标准

本轮实现完成后，应满足：

1. `lap-debug-mode` 的页面语义正式切换到 Track/LapTimingEngine 主链路；
2. 页面不再以 `LapDebugAnalyzer` 结果作为核心展示；
3. 页面明确标注当前第一阶段只支持 `起点 + s1`；
4. 用户能从执行页和结果页直接看出第一阶段链路是否成立；
5. `s2` 不再阻塞页面进入正式圈速入口第一阶段。

## 下一轮实施建议

下一轮实现只做一件事：

**把当前 `lap-debug-mode` 收口成 Track/LapTimingEngine 驱动的第一阶段正式圈速入口，并明确能力边界为 `起点 + s1`。**

不再并行推进：
- `s2` 资产修复
- 完整三门结果页
- 调试壳子继续扩写
- 双模式并存
