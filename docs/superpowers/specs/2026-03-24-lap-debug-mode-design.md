# 圈速调试模式设计

> 日期：2026-03-24
> 目标：在现有测试主链路上增加一套“圈速调试模式”，优先打通“开始测试 → 测试中 → 调试结果”的闭环，用于后续持续迭代圈速判定算法，而不是一次性做完整圈速产品。

## 1. 背景

当前项目已经具备一条完整但偏测速场景的测试主链路：

- 应用启动后进入 `TestFlowNavigation`
- 用户先连接设备，再进入测试选择页
- 选择测试类型后进入测试执行页
- 测试完成后进入结果页
- 历史页用于查看过往记录

当前这条链路主要服务于：

- 0-100 加速测试
- 100-0 刹车测试

它已经能承载：

- 测试前选择
- 测试中实时状态展示
- 测试后结果展示与历史记录

但对于“圈速记录”来说，当前缺少的是一条**可反复试验、可快速观察问题、可持续替换算法**的调试型闭环。用户当前最需要的不是成熟的圈速产品交互，而是：

1. 能尽快进入圈速测试
2. 测试中看到轨迹和关键命中状态
3. 测试后快速看到调试型结果
4. 后续持续替换判圈规则，而不需要反复重做页面主流程

因此，本阶段不应先投入完整导航规划，也不应直接做最终态圈速产品，而应优先建设一套“圈速调试模式”。

## 2. 设计目标

本设计需要满足以下目标：

1. **复用现有测试主链路**，避免为了圈速功能先重做全局导航
2. **支持模式切换**，让圈速能力以“测试模式”的形式接入现有流程
3. **支持测试前调试配置**，便于持续调整最小必需参数
4. **支持轨迹优先的实时页面**，方便调试判圈过程
5. **支持调试可读的结果页**，方便分析算法是否命中正确
6. **将算法逻辑与流程编排解耦**，避免后续判圈策略迭代时牵动整条测试状态机
7. **与当前代码结构相容**，优先沿着现有 `TestFlowNavigation` 主链路增量接入

## 3. 非目标

除了功能范围控制外，第一阶段还应遵守一个实现约束：**尽量避免污染现有普通测速链路与既有页面职责，优先通过新增圈速调试专用页面、专用结果模型和专用分析单元来隔离变化。**

本阶段明确不做以下内容：

- 完整的正式圈速产品信息架构
- 完整圈速历史管理体系
- 多套复杂判圈算法全面对比系统
- GPX/KML 导出
- 视频录制与视频合成
- 重做现有应用一级导航
- 一次性解决圈速算法准确性问题

本阶段的目标是：**先搭出一条可持续调试算法的产品壳子**。

## 4. 总体方案

采用 **“复用现有测试入口 + 增加圈速模式开关 + 插入圈速调试配置 + 分流到圈速实时页/结果页”** 的方案。

### 4.1 核心思路

现有测试主链路不变：

```text
连接设备 → 测试选择 → 测试执行 → 测试结果 → 历史记录
```

在此基础上，新增“测试模式”维度：

- 普通模式：延续现有测速逻辑
- 圈速调试模式：进入圈速调试配置、执行与结果链路

其本质不是新增一个新的一级产品模块，而是先把圈速作为现有测试体系中的一个实验模式接入。

### 4.2 第一阶段主路径

第一阶段明确采用**独立配置页**，而不是在选择页内展开配置区。

固定导航路径如下：

```text
Connection
  → Selection
  → LapDebugConfig
  → LapDebugExecution
  → LapDebugResult
```

其中：

- `Selection` 仍负责选择测试类型、车型和模式
- 当模式为普通模式时，仍沿用现有 `Selection → Execution → Result` 链路
- 当模式为圈速调试模式时，进入 `LapDebugConfig`，不直接跳到现有 `Execution`
- `LapDebugResult` 只服务本次调试会话复盘，不进入现有正式历史链路

### 4.3 第一阶段导航 contract

为了避免实现期歧义，第一阶段导航 contract 固定如下：

- `TestSelectionScreen` 输出：`template + carModel + mode`
- `LapDebugConfigScreen` 输出：`LapDebugConfig`
- `TestFlowNavigation` 根据 `mode` 选择普通测速链路或圈速调试链路
- 返回规则：
  - `LapDebugConfig → Selection`
  - `LapDebugExecution → LapDebugConfig`
  - `LapDebugResult → Selection`

这样做的好处是：

- 不需要先做完整导航规划
- 可以最快打通“可测试、可观察、可复盘”的闭环
- 与当前 `TestFlowNavigation` 的单路由状态管理方式相容
- 把“配置冻结点”固定在 `LapDebugConfigScreen` 提交时，避免测试开始后仍然修改实验参数

## 5. 页面与交互职责划分

## 5.1 测试选择页

现有 `TestSelectionScreen` 的职责目前是：

- 选择测试模板
- 输入车型
- 进入测试
- 查看历史记录

第一阶段扩展后，仍保持其作为统一入口，但职责收敛为：**只负责选择，不负责承载圈速详细配置**。

### 第一阶段新增职责

- 提供“普通模式 / 圈速调试模式”切换
- 在点击“进入测试”时输出 `template + carModel + mode`
- 当模式为圈速调试模式时，跳转到独立的 `LapDebugConfigScreen`
- 保持现有测试类型卡片与车型输入结构基本不变

### 推荐交互

- 仍先选测试类型
- 在“进入测试”前显示模式切换
- 普通模式：直接进入现有 `Execution`
- 圈速调试模式：进入 `LapDebugConfigScreen`

### 不建议做的事

- 第一阶段把圈速记录做成新的一级首页入口
- 第一阶段在选择页内塞入完整的圈速调试配置表单
- 第一阶段把测试选择页改造成完整的多模块控制中心

## 5.2 `LapDebugConfigScreen`

这是圈速模式第一阶段最关键的新增页面，用于承载后续持续调参。

### 目标

将原本可能写死在 ViewModel 或算法里的实验参数，前移到测试开始前配置，并在点击开始时冻结为一份 `LapDebugConfig`。

### 第一阶段最小必需配置

第一阶段只要求以下配置项：

- 起终点参考设置方式
- 命中阈值
- 是否显示轨迹
- 是否显示命中点

### 可以预留但不要求首轮完成的配置

- 判圈策略选择
- 是否显示原始采样点
- 是否显示候选圈/候选分段
- 其他调试显示项开关

### 边界

- 第一阶段不做复杂高级设置系统
- 第一阶段不要求支持多套策略矩阵对比
- 配置页提交后才进入执行页，执行中不允许修改配置

## 5.3 `LapDebugExecutionScreen`

现有 `TestExecutionScreen` 明显是面向普通测速设计的：

- 标题来自 `TestTemplate`
- 中心信息是速度与进度条
- 运行逻辑依赖普通测速的开始/结束条件
- 完成后会进入现有成绩页

因此第一阶段不建议在同一个屏里硬塞条件分支，而是新增独立的 `LapDebugExecutionScreen`。

### 第一阶段重点信息

- 当前轨迹
- 当前定位点
- 起终点线 / 命中区域
- 当前状态（待开始 / 记录中 / 已命中 / 已形成候选圈等）
- 当前候选圈或候选分段状态
- GPS 状态（卫星数、频率、HDOP）
- 采样点数量
- 当前速度等辅助数据

### 第一阶段运行规则

为避免强行复用现有测速触发逻辑，第一阶段固定采用：

- **手动开始记录**
- **手动停止记录**

也就是说：

- 进入 `LapDebugExecutionScreen` 后，用户显式点击开始
- 开始后持续采样并交给 `LapDebugAnalyzer`
- 用户显式点击停止后，生成 `LapDebugResult`
- 即使没有形成有效圈结果，也必须进入结果页，展示空候选圈及原因说明

### 原则

- 轨迹与命中可视化优先于成绩展示
- 让用户一眼看出“这次到底命中了哪里、轨迹是否合理”
- 第一阶段不要求做成完整地图产品，只要求形成足够清晰的调试执行页

## 5.4 `LapDebugResultScreen`

现有 `TestResultScreen` 偏“最终成绩展示页”，且数据入口依赖 `testId -> history -> dataFilePath`，不适合直接承担调试型圈速结果。

因此第一阶段必须新增独立的 `LapDebugResultScreen`，并明确采用**会话结果直传/驻留**方式，而不是走现有历史链路。

### 第一阶段结果页重点

- 原始轨迹
- 命中点或命中区可视化
- 候选圈/候选分段列表
- 每段耗时
- 当前使用的配置快照
- 基础统计信息
- 便于人工判断的调试说明

### 数据来源

第一阶段固定采用以下策略：

- `LapDebugResultScreen` 不复用 `TestResultScreen`
- `LapDebugResultScreen` 的数据来源为当前会话结束后保存在内存中的最近一次 `LapDebugResult`
- 第一阶段不写入现有 `TestHistory` 正式历史链路
- 若用户从结果页返回，默认回到 `Selection`，而不是进入 `History`

### 页面定位

这不是正式的“用户友好成绩页”，而是“调试复盘页”。

其主要用途是回答：

- 判圈是否发生在合理位置
- 候选圈是否分对了
- 是否因为轨迹漂移、采样稀疏或阈值设置导致误判

## 6. 数据流与状态流设计

## 6.1 现有结构问题

当前 `TestSessionViewModel` 主要承担：

- 测试状态机
- 启停逻辑
- 与 `TestTemplate` 相关的开始/结束判断
- 保存测试结果

这套结构对普通测速有效，但它本质上仍是**测速模板驱动状态机**：

- 启动依赖 `enterSmartLaunch(template, carModel)`
- 运行中依赖 `checkTriggerCondition(...)`
- 结束依赖 `template.shouldEnd(...)`
- 完成后依赖 `CalculateResultUseCase` 与现有结果存储链路

因此，如果把圈速分析逻辑全部直接塞进去，会导致：

- 流程编排和算法细节耦合
- 后续调策略时频繁修改状态机
- 普通测速与圈速调试相互污染
- 实现者误把圈速调试模式当作现有 `TestTemplate` 的简单新增 case

## 6.2 第一阶段职责边界

推荐拆成两层：

### 层 1：流程编排层
负责：

- 当前测试处于哪一阶段
- 当前走普通模式还是圈速调试模式
- 开始、取消、结束测试
- 导航与结果页跳转所需的会话状态

这一层仍主要由现有 `TestSessionViewModel` 承担，但第一阶段只建议做最小扩展：

- `currentMode`
- `lapDebugConfig`
- `latestLapDebugResult`
- `LapDebugAnalyzer` 生命周期管理

### 层 2：圈速调试分析层
负责：

- 接收实时 GPS 数据
- 基于圈速配置分析轨迹
- 识别命中点、命中区域、候选圈、候选分段
- 生成供执行页展示的实时调试状态
- 生成供结果页展示的调试结果

这一层应由新的 `LapDebugAnalyzer` 承担，而不是让 `TestSessionViewModel` 自己吞下全部细节。

### 第一阶段明确不复用的现有逻辑

为避免实现期误用，第一阶段明确约束如下：

- 圈速调试模式**不直接建模成现有 `TestTemplate` 的普通新增 case**
- 圈速调试模式**不依赖**现有 `template.shouldEnd(...)`
- 圈速调试模式**不走**现有 `CalculateResultUseCase`
- 圈速调试模式**不复用**现有 `TestResultScreen`
- 圈速调试模式**不写入**现有正式成绩历史链路

## 6.3 推荐数据流

```text
实时 GPS 数据
   ├─→ 普通测试流程（现有逻辑）
   └─→ LapDebugAnalyzer（新逻辑）
                ├─→ LapDebugState（给执行页）
                └─→ LapDebugResult（给结果页）
```

### 价值

这样后续调判圈算法时，主要修改的是 `LapDebugAnalyzer` 及其配置，而不是把整个测试链路打散重做。

## 7. 推荐的数据结构与职责单元

第一阶段推荐新增以下职责单元，并统一采用 `LapDebug*` 命名，减少后续实现歧义。

### 7.1 `LapDebugConfig`
职责：承载圈速调试模式开始前的所有配置。

第一阶段最小字段建议包括：

- 起终点参考信息
- 命中阈值
- 是否显示轨迹
- 是否显示命中点

### 7.2 `LapDebugState`
职责：承载测试执行中的实时调试可视状态。

建议字段类型包括：

- 当前轨迹点集合
- 当前定位点
- 命中状态
- 候选圈状态
- 采样统计
- 当前配置摘要

### 7.3 `LapDebugAnalyzer`
职责：基于实时 GPS 数据和配置，产出圈速调试状态与结果。

第一阶段建议能力包括：

- 轨迹累积
- 命中检测
- 候选圈/分段识别
- 调试结果生成

### 7.4 `LapDebugResult`
职责：承载测试结束后的圈速调试结果。

建议字段类型包括：

- 原始轨迹
- 命中点集合
- 候选圈列表
- 分段结果
- 配置快照
- 调试统计摘要

## 8. 与现有文件的关系

## 8.1 需要扩展的现有文件

### `feature/test/ui/TestFlowNavigation.kt`
新增能力：

- 新增 `LapDebugConfig`、`LapDebugExecution`、`LapDebugResult` 路由分支
- 根据模式类型决定走普通测速链路或圈速调试链路
- 明确圈速调试链路返回到 `Selection`，不接入现有 `History`

### `feature/test/ui/screen/TestSelectionScreen.kt`
新增能力：

- 模式切换
- 输出 `template + carModel + mode`
- 普通模式与圈速调试模式的入口分流

### `feature/test/viewmodel/TestSessionViewModel.kt`
新增能力：

- 管理当前模式
- 持有 `LapDebugConfig`
- 驱动 `LapDebugAnalyzer` 生命周期
- 持有最近一次 `LapDebugResult`

## 8.2 推荐新增的文件/单元

按职责新增：

- `LapDebugConfigScreen`
- `LapDebugExecutionScreen`
- `LapDebugResultScreen`
- `LapDebugConfig`
- `LapDebugState`
- `LapDebugResult`
- `LapDebugAnalyzer`

这些文件应尽量围绕“圈速调试模式”集中放置，避免打散在过多目录中。

## 9. 范围控制与迭代策略

为了保证第一阶段能快速落地并开始调算法，需要严格控制范围。

### 第一阶段必须具备

- 测试入口可开启圈速调试模式
- 测试前可配置最小必需调试参数
- 测试中可看轨迹与命中状态
- 测试后可看调试型结果
- 算法层与流程编排层具备基本边界
- 即使没有形成有效圈，也能完成一次调试闭环

### 第一阶段可以延后

- 正式圈速历史管理
- 高完成度产品化 UI
- 正式用户口径成绩页
- 视频叠加
- 多导出格式
- 复杂算法矩阵对比
- 组合模式（如“圈速 + 视频”）

## 10. 与后续能力的关系

本设计虽然聚焦圈速，但它有一个重要附加价值：它为现有测试主流程增加了一层“模式分流”能力。

第一阶段只要求这层结构**可扩展**，不要求显式实现视频模式，也不要求引入组合模式概念。

后续如果要加入视频录制/合成能力，可以沿着相同分流思路扩展，但这不属于本轮实现范围。

## 11. 实施建议

建议按以下顺序推进：

1. 先补圈速模式的数据结构与模式入口
2. 再补开始前配置承载
3. 接入圈速调试实时分析状态
4. 扩展执行页展示轨迹优先的调试视图
5. 新增圈速调试结果页
6. 最后再逐步迭代判圈策略本身

这样能尽快形成一条可实测、可观察、可复盘的调试链路。

## 12. 结论

本设计选择：

**不先做完整导航，不先做完整圈速产品，而是先在现有测试主链路上增加“圈速调试模式”。**

它的核心价值在于：

- 快速打通测试闭环
- 优先服务算法调试
- 控制第一阶段范围
- 为未来正式圈速功能和视频能力留出稳定扩展位

对于当前项目阶段，这是比“先做大导航”或“直接做最终态圈速产品”更稳妥、更高产出的路线。
