# Agent Team 治理与项目规则设计规范

> 日期：2026-03-24
> 目标：为 GPS Android 项目建立可审计、可恢复、可逐步演进的多 Agent 协作规则，降低主 Agent 上下文膨胀、幻觉、越权修改和 silent failure 风险
> 适用范围：项目规则、任务分发、关键任务门禁、团队生命周期、进度汇报、失败恢复

## 1. 设计目标

本设计不追求“角色越多越强”，而追求：

- **可放心托付**：用户提交任务后，流程具备门禁、审计和证据闭环
- **可解释**：每个阶段都有清晰负责人、输入、输出和退出条件
- **可恢复**：某个 Agent 卡住、失败或失联时，流程可以恢复，而不是静默停摆
- **低幻觉**：主 Agent 不直接承担实现与大规模读码，减少上下文快速填满导致的判断失真
- **可演进**：先落地最必要的治理规则，后续再根据实际运行体验补充

## 2. 总体原则

### 2.1 主从分离

采用 **主 Agent（orchestrator）与子 Agent（专职执行者）分离** 的结构。

- 主 Agent 负责：任务归类、门禁判断、角色召唤、阶段推进、证据汇总、有限只读核对、向用户汇报
- 子 Agent 负责：需求分析、实现、协议/数据兼容分析、测试验证、代码审查等专业工作

这样做的核心原因是：

1. 防止主 Agent 上下文被大量源码、日志、验证输出迅速填满
2. 防止主 Agent 一边实现、一边审查、一边汇报，导致职责混淆
3. 保持主 Agent 始终站在“调度与审计”视角，而不是“写代码的执行者”视角

### 2.1.1 文档分层说明

为兼顾“为什么这样设计”和“实际怎么执行”，本文按三层阅读：

- **第 1-5 章**：治理目标、原则、关键任务定义、角色体系、主 Agent 边界
- **第 6-10 章**：执行流程、Gate、团队生命周期、进度与恢复机制
- **第 11-13 章**：标准报告模板、落地文件、迁移方式与后续演进

读者可以按“先原则、再执行、最后模板”的顺序阅读，也可按需跳转。
### 2.2 双保险机制

项目采用 **流程审批 + 证据校验** 的双保险机制。

- **普通任务**：以证据校验为主，流程相对精简
- **关键任务**：强制前置分析、阶段门禁、证据核对和升级机制

### 2.3 证据优先于结论

任何“已完成”“已通过”“可提交”的结论，都必须建立在实际产物和验证证据之上。

允许的证据包括但不限于：
- 修改文件列表
- diff 摘要
- 兼容性说明
- 测试命令与输出
- 审查报告
- 阻塞/升级报告

### 2.4 测试先于实现

本项目采用“**测试用例先于实现**”的原则。

含义是：
- 在任务拆解完成后，tester 应优先给出测试方案、验收用例和回归清单
- implementer 不应在“完成标准尚未明确”时直接进入实现
- 对适合测试驱动开发的任务，优先采用 TDD：先有 failing test，再实现

该原则的目标不是机械化要求所有任务都先写自动化测试代码，而是确保：
1. 先定义“什么算完成”
2. 先定义边界与异常场景
3. 让实现、审查、验证共享同一套验收依据

## 3. 关键任务定义

以下变更默认归为 **关键任务**：

### 3.1 蓝牙核心链路
- BLE 扫描、连接、重连
- 蓝牙协议定义
- BLE 数据包解析
- RaceChrono / ESP32 相关协议兼容
- 蓝牙数据接收后的转换、过滤与入库前处理

### 3.2 数据结构与兼容性
- 蓝牙数据持久化设计
- 测试历史记录的数据结构
- 数据模型字段增删改
- 历史记录兼容、旧协议兼容、旧存储格式兼容

### 3.3 权限相关
- 权限申请流程
- 权限申请时机
- 权限文案与权限降级路径
- Android 版本差异（如 API Level 相关权限模型变化）
- 蓝牙扫描 / 连接 / 定位权限组合矩阵
- 前后台扫描限制与系统开关依赖

### 3.4 工程基础设施
- 项目结构
- 模块划分
- Gradle / 构建规则
- 项目规则文件本身
- team / agent 配置本身

### 3.5 任务分级与升级规则

为避免普通任务与关键任务在执行中发生口径不一致，任务分级采用以下规则：

#### 单类命中
- 只命中普通改动边界 → 普通任务
- 命中任一关键任务边界 → 关键任务

#### 多类命中
- 同时命中 BLE / 协议 / 数据兼容 / 工程基础设施中的多个类别时，可并行召唤多个 guardian
- orchestrator 负责记录命中依据，并以“更高风险类别”为准进行总体分级

#### 执行中升级
- 如果 implementer、reviewer、tester 或 guardian 在执行中发现任务越界，必须立即上报
- orchestrator 必须中断当前普通任务流程，将任务回退到 Gate 1（重新分级）或 Gate 2（补 guardian 影响分析）
- 回退前产生的实现产物保留，但不得直接进入完成门

#### 一票升级条件
出现以下任一情况，普通任务必须升级为关键任务：
- 发现 BLE 协议、数据包格式、数据解析规则受影响
- 发现历史记录或持久化结构兼容风险
- 发现需要调整项目结构、模块边界、构建规则或项目规则
- 发现 Android 权限申请逻辑、权限矩阵或系统版本差异处理受影响

#### 最终裁定权
- orchestrator 拥有任务分级的最终裁定权
- 但该裁定必须在任务单中记录依据，并接受 guardian / reviewer / tester 的升级建议约束
- 若角色之间存在分级冲突，必须升级给用户，而不是由某个执行角色单方面定案

不触及以上边界的局部低风险改动，可归为普通任务。

## 4. 角色体系

项目采用 **固定角色 + 条件触发角色** 模型。

### 4.1 常驻角色

#### orchestrator
主调度者。负责：
- 任务分类（普通 / 关键）
- 识别涉及模块
- 生成任务单
- 按需召唤子 Agent
- 收集与核对子 Agent 报告
- 向用户汇报当前状态与建议

#### implementer
实现角色。负责：
- 在明确任务单下进行代码修改
- 输出修改范围、实现摘要、风险与未覆盖项

#### tester-validator
验证角色。负责：
- 设计验证路径
- 执行或核对验证命令
- 输出验证证据与未覆盖项

#### reviewer-auditor
审计角色。负责：
- 检查代码质量
- 检查改动边界
- 检查是否违反项目规则
- 输出通过 / 有条件通过 / 退回修改结论

### 4.2 条件触发角色

#### product-analyst
当需求不清、验收标准不足、范围有歧义时介入。

#### protocol-data-guardian
当任务涉及 BLE、协议、数据解析、数据持久化、测试历史记录兼容时必须介入。

#### build-structure-guardian
当任务涉及项目结构、模块调整、Gradle 配置、规则文件、team 配置时必须介入。

#### ui-flow-analyst
当任务涉及用户可见流程、权限交互、测试流程体验时按需介入。

## 5. 主 Agent 行为边界

### 5.1 orchestrator 允许做的事
- 读取规则文件
- 读取子 Agent 报告
- 读取 diff
- 读取测试输出
- 读取最终候选文件做有限核对
- 汇总状态并向用户汇报

### 5.2 orchestrator 禁止做的事
- 直接写代码
- 直接编辑实现文件
- 进行**无边界的大规模读码探索**
- 替 implementer 产出实现
- 在没有 reviewer / tester 结论前宣布完成

> 注：主 Agent 可以进行 **有限只读核对**，包括围绕任务边界的有限探索、diff 核对、测试输出核对和候选文件核对，但不得退化成直接实现者。

## 6. 准入与退出条件

### 6.1 orchestrator

#### 准入条件
收到任务后必须先完成：
1. 任务归类
2. 涉及模块识别
3. 需要唤起的角色判断
4. 任务单生成

#### 退出条件
只有在以下都满足时，才能向用户提交“可确认状态”：
- 所需角色已交付报告
- 关键任务所需 guardian 已介入
- reviewer 已有结论
- tester 已有验证结果
- orchestrator 已完成有限只读核对

### 6.2 implementer

#### 准入条件
必须拿到：
- 明确任务单
- 改动范围
- 涉及模块 / 文件提示
- 验收标准
- 若为关键任务，还需看到 guardian 影响说明

#### 强制退出条件
实现报告提交后，必须停止继续扩改，除非：
- reviewer 退回
- tester 验证失败
- orchestrator 下达二次修改任务

### 6.3 reviewer-auditor

#### 准入条件
必须在 implementer 有明确产物后介入。

#### 退出结论只允许三种
- 通过
- 有条件通过
- 退回修改

### 6.4 tester-validator

#### 准入条件
验证分为三个阶段：

##### 测试前置（需求拆解后优先执行）
在 orchestrator 完成任务单，且 guardian / analyst 给出必要补充后，tester 应优先输出：
- 测试方案
- 验收用例
- 回归清单
- 若适用，failing test 设计建议

##### 基础验证（可在 reviewer 前执行）
用于尽早暴露构建、测试、场景和环境问题。tester 必须拿到：
- 改动范围
- 验收标准
- 需要验证的命令 / 场景

##### 完成验证（在 reviewer 结论后执行）
用于进入完成门前的最终确认。tester 额外需要拿到：
- reviewer 结论
- reviewer 提出的重点关注项

#### 退出要求
必须给出实际验证记录；没有证据输出，不得退出。

#### TDD 适用范围
以下任务应优先采用 TDD：
- `core/domain` 中的算法、过滤、计算逻辑
- 协议解析
- 数据结构兼容逻辑
- 历史记录读写转换
- bug 修复（先复现，再修复）

以下任务推荐测试先行，但不强制代码级 TDD：
- ViewModel 状态流转
- Repository 逻辑
- 权限判定逻辑

以下任务不强制 TDD，但仍应先定义验收用例：
- 纯 UI 布局
- 文案调整
- 规则文档
- team 配置

### 6.5 guardian 角色

#### 准入条件
命中触发规则即必须进入，不是可选建议。

#### 退出条件
必须给出：
- 影响面
- 风险评估
- 注意事项
- 是否允许进入实现阶段

## 7. 三道 Gate

### Gate 1：立项门
由 orchestrator 执行。

职责：
- 判断任务类型
- 判断是否为关键任务
- 判断需要召唤哪些角色
- 建立任务单

### Gate 2：实现门
由 guardian / orchestrator 共同约束。

规则：
- 关键任务没有 guardian 影响分析，不允许 implementer 开始

### Gate 3：完成门
由 reviewer-auditor、tester-validator 和 orchestrator 共同约束。

规则：
- 没有 reviewer 结论 + tester 验证 + orchestrator 核对，不允许向用户报告“已完成”

## 8. 任务流程

### 8.1 普通任务流程

```text
用户任务
  ↓
orchestrator 立项
  ↓
tester-validator 测试前置（验收用例 / 回归清单）
  ↓
implementer 实现
  ↓
tester-validator 基础验证（尽早暴露构建/场景问题）
  ↓
reviewer-auditor 审查
  ↓
tester-validator 完成验证
  ↓
orchestrator 汇总给用户
```

### 8.2 关键任务流程

```text
用户任务
  ↓
orchestrator 立项
  ↓
product-analyst（必要时补齐需求）
  ↓
protocol-data-guardian / build-structure-guardian（按类型强制介入，可多 guardian 并行）
  ↓
tester-validator 测试前置（验收用例 / 回归清单 / failing test 建议）
  ↓
implementer 实现
  ↓
tester-validator 基础验证（尽早暴露构建/协议/兼容问题）
  ↓
reviewer-auditor 审查
  ↓
tester-validator 完成验证
  ↓
orchestrator 汇总给用户
```

### 8.3 非编码任务快速通道

对于以下任务，不要求默认召唤 implementer 与 tester：
- 文档评审
- 方案对比
- 根因分析
- 规则审阅
- 配置评估

推荐最小组合：
- orchestrator
- analyst 或 guardian
- reviewer-auditor

如果在快速通道中发现任务已转为实现类任务，则必须重新回到 Gate 1 立项，而不是直接扩展执行范围。

## 9. 团队生命周期与召回策略

### 9.1 何时召唤团队

**不在用户刚提需求时立刻拉全队。**

正确做法：
1. orchestrator 先单独完成任务归类、模块识别和任务单生成
2. 在任务单形成后，再按需召唤所需角色

#### 普通任务召唤
- implementer
- reviewer-auditor
- tester-validator

#### 关键任务召唤
- 对应 guardian
- implementer
- reviewer-auditor
- tester-validator
- 必要时 product-analyst / ui-flow-analyst

### 9.2 阶段性退出
某个子 Agent 完成自己职责并交付报告后，即进入 idle / 可回收状态，不继续占用主流程。

### 9.3 团队整体解散
当以下条件满足时，orchestrator 应主动解散本次团队：
- 最终报告已汇总给用户
- 用户已决定继续 / 修改 / 结束
- 当前任务没有待执行分支
- 没有挂起的 reviewer / tester / guardian 复查请求

推荐原则：
- 按任务召唤
- 按任务解散
- 子 Agent 临时存在
- orchestrator 可在一个会话内短驻，连续协调多个任务

## 10. 故障恢复与进度可观测性

### 10.1 阻塞必须上报
当出现以下情况时，子 Agent 必须主动上报阻塞：
- 找不到文件
- 范围不清
- 验证命令失败
- 审查结论冲突
- 修改需要跨模块扩大范围
- 权限或环境阻塞

### 10.2 任务状态外部化
任务状态不能只存在 Agent 上下文中。orchestrator 必须维护至少以下状态：
- 当前阶段
- 当前负责人
- 已交付产物
- 阻塞点
- 是否需要重派

#### 最小状态载体
- 默认使用共享 task list / 任务卡作为最小状态载体
- 普通任务无需额外落盘
- 关键任务、跨会话任务或需要人工接管的任务，可额外写入设计文档、任务文件或规则附录中的状态记录区

### 10.3 超时恢复策略
如果在预期窗口内没有收到阶段产物或心跳，orchestrator 必须执行：
1. 轻量探测：确认该 Agent 是否仍在执行
2. 任务重派：转派给同类角色的备用 Agent
3. 升级给用户：说明卡点、已尝试动作、建议决策

### 10.3.1 默认时间参数
为避免“有原则但无法执行”，先定义一组保守默认值，后续可按实际协作体验微调：

#### 关键任务
- 心跳周期：15 分钟
- 连续 20 分钟无心跳或无阶段产物 → 触发轻量探测
- 连续 30 分钟无响应 → 允许重派
- 同一任务连续 2 次重派仍失败 → 必须升级给用户

#### 普通任务
- 默认不强制心跳
- 连续 20 分钟无阶段产物 → 触发轻量探测
- 连续 30 分钟无响应 → 允许重派或升级

#### 说明
- 短时分析任务可不等完整周期，只要在阶段完成时立即汇报
- 如果任务天然需要长时间等待外部验证，orchestrator 应在任务单中显式标记“等待型任务”，并调整探测预期窗口

### 10.4 阶段汇报
所有任务都必须在以下节点汇报：
- 已接单
- 影响分析完成
- 实现完成
- 审查完成
- 验证完成
- 任务阻塞
- 任务退回
- 可交付

### 10.5 关键任务心跳机制
关键任务必须开启周期性心跳；普通任务默认不强制，仅在接近超时或明显无产出时触发。

#### 心跳内容
```md
## 进度心跳
- 当前阶段：
- 当前动作：
- 是否阻塞：
- 下一步：
```

该机制的目的：
1. 防止 Agent 死掉或卡住而外部无感知
2. 防止 Agent 长时间埋头工作却没有进度反馈，导致流程不透明

## 11. 标准报告模板

### 11.1 orchestrator 汇总报告

```md
## 任务汇总

**任务类型**：普通 / 关键
**任务分类依据**：
- [命中规则 1]
- [命中规则 2]

**涉及模块**：
- core/bluetooth
- core/domain
- core/data
- feature/test
- simulator

**参与角色**：
- ...

### 本轮结论
- 当前状态：[可确认 / 待确认 / 已退回]
- 是否建议用户人工介入：[是 / 否]
- 是否允许进入下一步：[是 / 否]

### 项目专项核对
- BLE 链路阶段影响：[扫描 / 连接 / 订阅 / 解析 / 无]

### 变更摘要
- ...

### 风险摘要
- ...

### 验证摘要
- 命令：[命令]
- 结果：[通过 / 失败 / 部分通过]

### 待用户确认
- ...
```

### 11.2 implementer 报告

```md
## 实现报告

**任务ID**：
**改动范围**：
```

## 12. 项目落地文件

建议最终形成以下文件：

```text
CLAUDE.md
.claude/
├── PROJECT_RULES.md
└── android-dev-team.json
docs/superpowers/specs/
└── 2026-03-24-agent-team-governance-design.md
```

### 文件职责
- **CLAUDE.md**：高优先级、短规则、强约束入口
- **.claude/PROJECT_RULES.md**：完整治理细则
- **.claude/android-dev-team.json**：机器可消费的 team 配置
- **design spec**：记录设计 rationale，便于后续按项目运行情况逐步补充

### 12.1 规则优先级
治理落地后，规则优先级建议如下：

1. 用户直接指令
2. 项目根 `CLAUDE.md`
3. `.claude/PROJECT_RULES.md`
4. `.claude/android-dev-team.json` 中的角色职责与流程约束
5. design spec（设计依据，不直接替代运行规则）

### 12.2 迁移方式
为降低一次性改动风险，建议按以下顺序迁移：

1. 先创建项目根 `CLAUDE.md`，只放最小硬规则
2. 再创建 `.claude/PROJECT_RULES.md`，承载完整治理细则
3. 然后重写 `.claude/android-dev-team.json`，使其角色与流程对齐本设计
4. 最后在实际任务中试运行，再根据体验微调模板与角色触发规则

### 12.3 现有规则衔接
- 全局规则继续保留，用于通用安全边界与默认行为
- 项目根 `CLAUDE.md` 负责覆盖本仓库特有的高优先级治理要求
- `.claude/PROJECT_RULES.md` 负责补充细则，不重复堆砌在 `CLAUDE.md`
- team 配置应服从项目规则，而不是反过来定义项目规则

## 13. 演进策略

本设计只固化当前最必要的治理规则，不追求一次性穷尽所有细节。

后续应基于实际运行情况增补的方向包括：
- 哪些任务会频繁触发误判，需要重新细化关键任务边界
- 哪些角色 prompt 需要收缩或加强
- 心跳频率是否过高或过低
- 哪些报告模板字段是低价值噪音
- 哪些模块需要新增专项 guardian

### 13.1 治理效果评估指标
为避免后续仅凭主观感受调整规则，建议至少跟踪以下指标：
- 关键任务误分类率
- 任务执行中升级为关键任务的比例
- silent failure 次数（需要超时探测后才发现的任务）
- 重派率与重派成功率
- 关键任务返工率
- 用户人工介入率

这些指标不要求一开始就自动化，但应在实际协作中逐步记录，用于后续迭代规则。

原则是：**先建立足够可靠的骨架，再根据真实协作体验补充。**
